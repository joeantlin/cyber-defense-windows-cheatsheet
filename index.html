PowerShell Fundamentals
▶Set-Content— write or overwrite a file's contents
Definition

Writes text to a file, replacing whatever was there before. A clean example of PowerShell's verb-noun cmdlet naming — the verb (Set) and noun (Content) describe exactly what it does, no memorizing an unrelated word the way cat or echo require in a Unix shell.

Use Case (Cyber Defense context)

Quick way to plant or patch config content from a script, or to overwrite a file's contents as part of cleanup — for example, blanking out a log a script needs to reset, or writing a known-good config back after tampering.

Syntax
PS> Set-Content -Path <string> -Value <string>
Examples
# Overwrite a file with a single line
PS> Set-Content -Path .\status.txt -Value "clean"
Notes

Set-Content replaces the entire file. To append instead of overwrite, use Add-Content with the same syntax — same cmdlet family, different verb.

See Also
Get-Content, Get-ChildItem
▶Invoke-Expression— run a string as a PowerShell command⚠ risk
Definition

Takes a string and executes it as if it had been typed directly into the shell. Often shortened to its alias, iex.

Use Case (Cyber Defense context)

Legitimate uses exist (dynamically building a command from variables), but from a defensive standpoint this is more important to recognize than to run yourself — it's one of the most common execution steps in fileless PowerShell malware, letting an attacker download a script into memory and run it without ever writing a file to disk.

Syntax
PS> Invoke-Expression -Command <string>
PS> iex <string>   # same thing, common alias
Examples
# Build and run a command from a variable
PS> $cmd = "Get-Process"
PS> Invoke-Expression $cmd
Caution

Treat unexpected iex usage in a script, scheduled task, or command history as a red flag worth investigating — especially patterns like iex (New-Object Net.WebClient).DownloadString(...), a well-known download-and-execute pattern for pulling a script from the internet straight into memory.

See Also
Invoke-Command
▶Get-Member— discover an object's properties and methods
Definition

Shows every property and method available on whatever gets piped into it. Since everything in PowerShell is an object rather than plain text, this is how you actually discover what you have to work with instead of guessing at a property name.

Use Case (Cyber Defense context)

Facing an unfamiliar cmdlet's output and needing to know exactly what's filterable or sortable — run the cmdlet once, pipe it here, and the full field list is right there instead of hunting through documentation.

Syntax
PS> <command> | Get-Member
Examples
# What can I actually filter/sort on here?
PS> Get-Process | Get-Member

# Just the properties, skip the methods
PS> Get-Service | Get-Member -MemberType Property

Definition

Converts piped-in objects into CSV rows and writes them to a file — the object model's answer to redirecting output to a file, keeping actual columns instead of flattening everything into plain text.

Use Case (Cyber Defense context)

Documenting findings for a report or business inject — exporting a list of local users, running services, or firewall rules as evidence that opens cleanly in Excel.

▶Get-ChildItem— list files and directories
✓
RecommendedPrefer this over dir (cmd.exe) — it returns real objects you can pipe into Where-Object, Sort-Object, or Select-Object, instead of plain text you'd have to parse line by line.
Definition

Lists the items in a directory (or another PowerShell provider, like the registry). With no argument, lists the current working directory. Commonly reached via its built-in aliases, ls and dir — both just call this cmdlet under the hood.

Use Case (Cyber Defense context)

First command run in almost any directory to see what's actually there — -Force surfaces hidden and system files that might be a dropped payload or persistence mechanism, and -Recurse turns it into a fast way to hunt for a specific filename across an entire tree.

Syntax
PS> Get-ChildItem [-Path] <string> [-Recurse] [-Force] [-Filter <string>]
Relevant Options
FlagWhat it does
-ForceInclude hidden and system files/folders
-RecurseDescend into every subdirectory
-FilterWildcard filter applied by the provider itself — faster than piping to Where-Object
-PathTarget directory or provider path — defaults to the current location if omitted
Examples
# Everything in the current directory, hidden/system files included
PS> Get-ChildItem -Force

# Hunt for every PowerShell script under C:\Users, any depth
PS> Get-ChildItem -Path C:\Users -Filter "*.ps1" -Recurse
Notes

Because ls and dir are just aliases pointing back to this cmdlet, typing either one inside PowerShell runs Get-ChildItem — not a Unix ls and not cmd.exe's native dir. The dir card in this doc covers that separate, real cmd.exe command.

See Also
dir, Remove-Item, New-Item

▶Remove-Item— delete files, directories, or other provider items⚠ risk
Definition

Deletes files, directories, or items from other PowerShell providers (registry keys, certificates, etc.). Like most shell delete commands, there's no recycle bin in the loop — deletion is immediate.

Use Case (Cyber Defense context)

Cleaning up dropped tooling, removing a persistence artifact's backing file once it's been captured for evidence, or deleting a malicious scheduled task's payload.

Syntax
PS> Remove-Item [-Path] <string> [-Recurse] [-Force] [-WhatIf]
Relevant Options
FlagWhat it does
-RecurseDelete a directory and everything inside it
-ForceRemove hidden, read-only, or system items without prompting
-WhatIfPreview what would be deleted without deleting anything
Examples
# Remove a single file
PS> Remove-Item .\old_notes.txt

# Sanity-check a recursive delete before it actually runs
PS> Remove-Item .\tmp_build -Recurse -WhatIf

# Now actually remove the directory and everything inside it
PS> Remove-Item .\tmp_build -Recurse -Force
Caution

Irreversible — there's no recycle bin behind this cmdlet. -Recurse -Force on the wrong path can wipe far more than intended; run with -WhatIf first on anything scripted, wildcarded, or uncertain.

See Also
Get-ChildItem

▶Get-FileHash— generate a file's cryptographic hash
Definition

Computes a cryptographic hash of a file's contents — SHA256 by default. Two files with the same hash are identical byte-for-byte; a changed hash means the file changed.

Use Case (Cyber Defense context)

Confirm a file's integrity, or check it against a known-bad hash from an IOC list. IOC lists often ship as MD5 or SHA1 rather than SHA256, so matching the algorithm to whatever list you're checking against matters.

Syntax
PS> Get-FileHash -Path <string> [-Algorithm <string>]
Relevant Options
AlgorithmNotes
SHA256Default — use unless you have a specific reason not to
SHA1 / MD5Weaker, but still common in older IOC lists — match what you're comparing against
Examples
# Default SHA256
PS> Get-FileHash .\suspicious.exe

# Match an IOC list published as MD5
PS> Get-FileHash .\suspicious.exe -Algorithm MD5
See Also
Get-AuthenticodeSignature, Compare-Object, Windows Defender
▶Get-AuthenticodeSignature— check a file's digital signature
Definition

Checks whether a file carries a valid digital signature and reports who signed it.

Use Case (Cyber Defense context)

A quick trust check on an unfamiliar executable — unsigned, or signed by an unexpected publisher, is worth flagging immediately, especially for anything sitting in a location like System32 where everything is normally signed by Microsoft.

Syntax
PS> Get-AuthenticodeSignature -FilePath <string>
Examples
# Who actually signed this, and is the signature valid?
PS> Get-AuthenticodeSignature C:\Windows\System32\suspicious.exe | Select-Object Status, SignerCertificate
Notes

A Valid status only confirms the signature itself is intact — not that the file is trustworthy. Signed malware exists; treat this as one signal to weigh, not a final verdict.

See Also
Get-FileHash, Windows Defender
▶Compare-Object— diff two sets of objects
Definition

Compares two collections of objects — file contents, directory listings, anything — and reports exactly what differs between them.

Use Case (Cyber Defense context)

Diffing a config against a known-good backup to see exactly what changed, or diffing two directory listings to catch a newly dropped file.

Syntax
PS> Compare-Object -ReferenceObject <object[]> -DifferenceObject <object[]>
Examples
# What actually changed in this config?
PS> Compare-Object (Get-Content .\known_good.conf) (Get-Content .\current.conf)

# Any new files dropped compared to a clean baseline?
PS> Compare-Object (Get-ChildItem C:\Windows\System32) (Get-ChildItem \\backup\System32_baseline) -Property Name
Notes

The output's SideIndicator column shows which side each difference came from — <= means it's only in the reference object, => means it's only in the difference object.

Permissions & Ownership
▶Get-Acl / Set-Acl— view or set a file/folder/registry key's access control list
Definition

Reads or writes the Access Control List (ACL) on a file, folder, or registry key — Windows' permission model, which is far more granular than Linux's owner/group/other: any number of individual users or groups can each have their own allow/deny entry on the same object.

Use Case (Cyber Defense context)

Checking exactly who has access to a sensitive file or folder, or restoring a known-good ACL onto something that's been tampered with.

Syntax
PS> Get-Acl -Path <string>
PS> Set-Acl -Path <string> -AclObject <object>
Examples
# Who actually has access to this webroot?
PS> Get-Acl C:\inetpub\wwwroot | Format-List

# Copy a known-good ACL onto a folder that's been tampered with
PS> $acl = Get-Acl .\good_folder
PS> Set-Acl .\bad_folder $acl
Notes

Set-Acl generally needs an ACL object built from Get-Acl rather than typed by hand — the two-step pattern in the example above (grab a good ACL, apply it elsewhere) is the common way this actually gets used.

See Also
icacls, Get-SmbShare

▶Set-ItemProperty— set a registry value⚠ risk
✓
RecommendedPrefer this over reg add when you're already in PowerShell — same registry provider as Get-ChildItem, so it composes with the rest of the pipeline instead of needing its own separate syntax.
Definition

Sets the value of a property on an item — most often a registry key, since PowerShell exposes the registry as just another provider it can navigate like a filesystem. Most Windows configuration ultimately traces back to a registry key somewhere, so this is the general-purpose tool for editing one directly.

Use Case (Cyber Defense context)

Toggling a security-relevant setting from the command line instead of digging through a GUI panel — enabling/disabling Remote Desktop or UAC, for example. Also worth checking as a persistence vector: a Run key holding an unexpected value can mean something launches automatically at login.

Syntax
PS> Set-ItemProperty -Path <registry path> -Name <property> -Value <value>
Examples
# Enable Remote Desktop (0 = allow connections)
PS> Set-ItemProperty -Path 'HKLM:\System\CurrentControlSet\Control\Terminal Server' -Name fDenyTSConnections -Value 0

# Re-enable UAC if it's been turned off (1 = enabled, the default)
PS> Set-ItemProperty -Path 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System' -Name EnableLUA -Value 1
Caution

There's no undo — setting the wrong value, or the right value in the wrong key, can break the feature it controls or destabilize the system. Confirm the exact path and value type before running, especially on a box you don't have console access to as a fallback.

See Also
reg add

▶New-LocalUser / Add-LocalGroupMember / Disable-LocalUser— create, add to a group, or disable a local account⚠ risk
Definition

Three related cmdlets covering the actions that follow an account audit: create a new account, change its group membership, or take an unauthorized one out of action. Grouped together here since they're usually reached for as a set, not one at a time.

Use Case (Cyber Defense context)

After Get-LocalUser turns up an account that shouldn't exist or shouldn't be enabled — disable it first rather than deleting outright, so it can still be reviewed before being removed for good.

Syntax
PS> New-LocalUser -Name <string> -Password <securestring>
PS> Add-LocalGroupMember -Group <string> -Member <string>
PS> Disable-LocalUser -Name <string>
Examples
# Create a new local account with a prompted, masked password
PS> New-LocalUser -Name "svc_backup" -Password (Read-Host -AsSecureString "Password")

# Add it to a group after it's created
PS> Add-LocalGroupMember -Group "Backup Operators" -Member "svc_backup"

# Take an unauthorized account out of action without deleting it yet
PS> Disable-LocalUser -Name "suspicious_acct"
Caution

Disabling the wrong account can lock out a legitimate user or service. Remove-LocalUser exists for permanent deletion, but it's a one-way action — disabling first preserves the account for investigation.

Changes settings on an existing local account — most often used to reset the password.

Resetting a potentially compromised account's password immediately, rather than waiting to fully investigate first.

Service Management
▶Get-Service— list services and their status
Definition

Lists services and whether each is running, stopped, or in another state. Services are background binaries that provide OS or third-party functionality — a native drive-encryption feature and a third-party FTP server are both examples.

Use Case (Cyber Defense context)

Baseline what's running, then watch for a service that shouldn't be there — some attacks spin up a temporary service specifically to spawn a shell as the SYSTEM account.

Syntax
PS> Get-Service [[-Name] <string[]>]
Examples
# Everything currently running
PS> Get-Service | Where-Object Status -eq Running
Notes

Services have both a display name (readable, e.g. "World Wide Web Publishing Service") and a shorter service name used internally (e.g. W3SVC). -Name here expects the short service name, not the display name — use -DisplayName instead if that's what you have.

See Also
Start-Service / Stop-Service / Set-Service

Use Case (Cyber Defense context)

Stopping an unauthorized service found during a Get-Service review, or disabling its startup type so it doesn't just come back on the next reboot.

PS> Start-Service -Name <string>

PS> Set-Service -Name <string> -StartupType <Automatic|Manual|Disabled>

Firewall
▶Get-NetFirewallRule / New-NetFirewallRule / Enable-NetFirewallRule— view, create, or turn on Windows Firewall rules⚠ risk
✓
RecommendedPrefer this over netsh advfirewall — faster to work with for scripting and automation, and reads more intuitively once you know the parameter names.
Definition

Windows Firewall is stateful — it automatically allows return traffic for connections you initiated, so rules only need to cover new inbound and outbound traffic you actually want to allow or block. Get-NetFirewallRule lists existing rules; New-NetFirewallRule creates one from scratch. Enable-NetFirewallRule is a distinct third case worth knowing — many rules already exist out of the box but sit disabled, so turning one on is a different action from creating a new one.

Use Case (Cyber Defense context)

Locking down what's allowed in and out — allow only the ports your actual services need inbound, and allow outbound only to what the box genuinely depends on.

Syntax
PS> Get-NetFirewallRule
PS> New-NetFirewallRule -DisplayName <string> -Direction <Inbound|Outbound> -Action <Allow|Block> [-LocalPort <int>] [-Program <string>]
PS> Enable-NetFirewallRule -DisplayName <string>
Examples
# See every current rule
PS> Get-NetFirewallRule

# Allow inbound SSH
PS> New-NetFirewallRule -DisplayName "Allow SSH" -Direction Inbound -Action Allow -LocalPort 22 -Protocol TCP

# Allow inbound HTTPS — prefer this over a plain HTTP rule where the choice exists
PS> New-NetFirewallRule -DisplayName "Allow HTTPS" -Direction Inbound -Action Allow -LocalPort 443 -Protocol TCP

# Turn on the built-in rule that allows inbound ping — it exists already, just disabled by default
PS> Enable-NetFirewallRule -DisplayName "File and Printer Sharing (Echo Request - ICMPv4-In)"
Notes

Windows blocks inbound ping by default — not because there's no rule for it, but because the built-in rule for it ships disabled. Enable-NetFirewallRule -DisplayGroup "File and Printer Sharing" would also work, but turns on all 14 rules in that group (SMB, NetBIOS, LLMNR included) — far more than ping alone needs. Targeting the exact rule by -DisplayName, as shown above, only opens what was actually asked for.

Caution

A rule that's broader than intended — wrong direction, wrong port, or allowing a whole program instead of a specific port — can open exposure you didn't mean to create. Review the exact scope before applying.

See Also

▶CREATE USER / GRANT— manage database users and privileges⚠ risk
Definition

SQL statements (run inside an active mysql session) for creating a database account and controlling exactly what it's allowed to do.

Use Case (Cyber Defense context)

The database-side version of the same question asked about file shares and web logins: what should be able to access this data, and with what privileges. A web application's database account should almost never have the same privileges as the account used to administer the database itself.

Syntax
CREATE USER '<username>'@'<host>' IDENTIFIED BY '<password>';
GRANT <privileges> ON <database>.<table> TO '<username>'@'<host>';
Examples
-- A web app account, scoped to only what it needs
CREATE USER 'webapp'@'localhost' IDENTIFIED BY 'REPLACE_ME';
GRANT SELECT, INSERT, UPDATE ON app_db.* TO 'webapp'@'localhost';

-- Confirm what a given account is actually allowed to do
SHOW GRANTS FOR 'webapp'@'localhost';
Notes

The @'<host>' part matters — 'user'@'localhost' and 'user'@'%' (any host) are different accounts entirely, even with the same username. A remotely-reachable account is a meaningfully different exposure than one restricted to local connections only. CREATE USER and GRANT both take effect immediately — FLUSH PRIVILEGES isn't actually required after them, despite showing up in a lot of tutorials out of habit. It's genuinely only needed after someone edits the underlying grant tables directly by hand, which normal account management never does.

Caution

GRANT ALL PRIVILEGES is tempting as a shortcut but hands out far more than almost any application account actually needs — scope grants to the specific privileges (SELECT, INSERT, UPDATE) and the specific database the account actually touches.

▶ 03 Quick Start & Routine Checks 7 tracks
Six separate tracks: A is one-time orientation — figure out what box you're on before anything else, run once, first. B is read-only recon, meant to be repeated — safe to run any time, on any box. C, D, E, and F actively change the system or query a domain, so they're kept separate from recon and from each other. Run A, then B. Only move into C, D, E, or F once you understand what's already there.
▶ A Environment Identification run once, first
One-time orientation, not something to repeat every session — figure out what box you're actually standing on before anything else. Nothing here changes the system.
  1. Confirm the PowerShell version
    The single most useful first command — everything else about what's available depends on this.
    PS> $PSVersionTable
    Results from $PSVersionTable
    PSVersion is 5.1
    MeansWindows PowerShell — the version built into Windows by default. Most cmdlets in this doc apply here without any extra setup.
    PSVersion is 7.x
    MeansPowerShell 7 (PowerShell Core) — a separately-installed, cross-platform version. Newer syntax and cmdlets may be available beyond what 5.1 has.
    Command isn't recognized at all
    MeansNot actually in PowerShell — likely cmd.exe or a restricted shell. Confirm what shell this actually is before continuing with anything else in this doc.
  2. Confirm the Windows edition and build
    Determines which cmdlets from this doc will even be available — Server-only cmdlets like Get-WindowsFeature simply don't exist on a Client edition.
    PS> Get-ComputerInfo | Select-Object WindowsProductName, OsVersion, OsBuildNumber
    Results from Get-ComputerInfo
    WindowsProductName contains "Server"
    MeansServer edition — Server-only cmdlets like Get-WindowsFeature/Install-WindowsFeature apply here.
    WindowsProductName contains "Windows 10" or "Windows 11"
    MeansClient edition — no Roles & Features module. Don't expect Get-WindowsFeature to work here.
    An unusually old OsBuildNumber
    MeansWorth checking against known CVEs tied to that specific build before assuming the box is current.
  3. Confirm domain membership and hostname
    Whether the box is domain-joined or standalone changes which cmdlets in Section 1's Active Directory category will actually return anything.
    PS> Get-ComputerInfo -Property CsName, CsDomain, CsPartOfDomain
    Results from Get-ComputerInfo -Property CsPartOfDomain
    CsPartOfDomain is True
    MeansDomain-joined — Get-ADUser/Get-ADComputer/Get-ADGroup can return real results (given the RSAT module), and WinRM trusts other domain members by default.
    CsPartOfDomain is False
    MeansStandalone/workgroup — the AD cmdlets won't return anything meaningful, and PS Remoting needs TrustedHosts configured manually rather than relying on implicit domain trust.
  4. Inventory commonly-needed tools — read-only, nothing gets installed here
    A quick pass to see what's already available versus what would need installing later. This step only reports what's present — it installs nothing.
    # Is winget available at all?
PS> Get-Command -Name winget -ErrorAction SilentlyContinue

# Is the RSAT Active Directory module installed?
PS> Get-Module -ListAvailable -Name ActiveDirectory

# (Server only) Is the IIS web server role already installed?
PS> Get-WindowsFeature -Name Web-Server
    What to look for: nothing returned just means it's not there yet — worth noting, not something to fix right now.
▶ B Routine Recon Checks read-only, repeatable
Look and understand before you touch anything. Nothing in this track changes the system. Unlike Track A, this one is meant to be repeated — rerun periodically, not just once. The same categories below double as a troubleshooting order when something's actually broken, not just being audited: check service status first, then network reachability, then logs for what actually happened, then authentication (a changed password, an expired credential) last — in that order, since chasing network connectivity on a service that's simply stopped wastes time on the wrong layer.
  1. Audit local users and groups
    Who exists, and who's actually privileged.
    PS> Get-LocalUser                                    # every local account and its enabled state
PS> Get-LocalGroupMember -Group "Administrators"     # who's actually privileged
    Results from Get-LocalUser / Get-LocalGroupMember
    An enabled account you don't recognize
    MeansWorth investigating immediately — see Disable-LocalUser once confirmed unauthorized
    A member of Administrators that shouldn't have that access
    MeansPrivilege escalation already happened, or a misconfiguration granted more access than intended — either way, worth acting on now
  2. Review running services
    Look for anything that shouldn't be there, and cross-check against recent service-creation events.
    PS> Get-Service | Where-Object Status -eq Running
    What to look for: a service you don't recognize by display name. Pair with Get-WinEvent filtered to Event ID 7045 to see exactly when and how it was installed.
  3. Review running processes
    Look for anything unfamiliar, oddly named, or running from an unusual path.
    PS> Get-Process | Sort-Object CPU -Descending | Select-Object -First 15
    What to look for: a process running from a temp directory or an unusual location; an unfamiliar process consuming a disproportionate amount of CPU. Pair with Get-NetTCPConnection's OwningProcess field if a suspicious network connection needs tracing back to the process behind it.
  4. Check scheduled tasks for persistence
    A classic way for access to survive a reboot or an initial cleanup.
    PS> Get-ScheduledTask | Select-Object TaskName, State
    What to look for: a task you don't recognize, especially one triggered at startup or logon. See Unregister-ScheduledTask once confirmed unauthorized.
  5. Check listening ports and active connections
    Just looking here — full network configuration lives in Track D.
    PS> Get-NetTCPConnection -State Listen
    Results from Get-NetTCPConnection
    A listening port that doesn't tie back to a service intended to run
    MeansWorth identifying the exact process behind it via the OwningProcess field and Get-Process
    A port bound to 0.0.0.0 rather than a specific local address
    MeansReachable from any interface, not just localhost — confirm that's actually intended
  6. Review the current firewall rule set
    See what's currently allowed. Building or changing rules lives in Track C — this step is only about seeing what's already there.
    PS> Get-NetFirewallRule | Where-Object Enabled -eq True | Select-Object DisplayName, Direction, Action
    What to look for: an inbound Allow rule on a sensitive port that isn't scoped to a trusted source, or a rule that doesn't match any service actually installed on the box.
  7. Document everything
    Write down what you found before moving into Track C, D, E, or F — this is your baseline. Export-Csv is the quickest way to turn any of the above into something you can hand off.
▶ C Firewall Setup & Hardening changes the system
Building or changing Windows Firewall rules — moves past just seeing what's already there. See Get-NetFirewallRule / New-NetFirewallRule and Windows Firewall for the full reference.
  1. Define what actually needs to be reachable — and just as important, what doesn't
    List the management access this box needs (e.g. RDP, WinRM) and the service ports it legitimately serves, before writing a single rule. For everything else running on the box, the real question isn't "should I firewall it" — it's "does this need to run at all."
    A real example of that decision
    SSH is running, but only a website and file share are actually scored
    Worth checking firstDoes the file share actually depend on SSH-based file transfer (SFTP) before touching anything — killing SSH could break the very thing being scored
    If it's confirmed unrelatedDisabling the service outright (Stop-Service + -StartupType Disabled) closes it for good — a firewall rule alone leaves the service itself still running and reachable from anywhere the rule doesn't cover
  2. Confirm which firewall profile is actually active
    Rules can be scoped to a specific profile — a rule written for the wrong one will silently never apply.
    PS> Get-NetConnectionProfile
    What to look for: the NetworkCategory field — Domain, Private, or Public. Write rules against whichever profile is actually active, or against all three if the box's network context might change.
  3. Write allow rules for that list
    Every port or program that needs to stay reachable gets an explicit Allow rule.
    # Allow RDP
PS> New-NetFirewallRule -DisplayName "Allow RDP" -Direction Inbound -Action Allow -LocalPort 3389 -Protocol TCP

# Allow a web server on port 80
PS> New-NetFirewallRule -DisplayName "Allow HTTP" -Direction Inbound -Action Allow -LocalPort 80 -Protocol TCP
  4. Confirm the default inbound action is still Block
    Unlike a Linux firewall, Windows Firewall ships with an implicit default-deny on inbound traffic per profile — there's no separate step to set it up. This step is only about confirming it hasn't been changed to Allow.
    PS> Get-NetFirewallProfile | Select-Object Name, DefaultInboundAction, DefaultOutboundAction
    What to look for: DefaultInboundAction should read Block for every profile in use. If it reads Allow, that's a serious misconfiguration — anything not explicitly blocked is getting through.
  5. Verify from a second session before closing your current one
    If managing this box remotely via RDP or PS Remoting, open a second connection attempt to confirm access still works before closing the session you're currently working in.
  6. Document exactly what's open and why
    Every allowed port, tied to the service that needs it. Makes the next audit — and the next person — much faster.
▶ D Network Setup & Configuration changes the system
IP configuration, adapters, and related network settings — full setup, not just the read-only look from Track B. See Get-NetAdapter and New-NetIPAddress / Set-DnsClientServerAddress for the full reference.
  1. Identify the interface and its current state
    Confirm which adapter you're configuring and its interface index — every other cmdlet in this track needs that index.
    PS> Get-NetAdapter
  2. Assign the intended static IP and default gateway
    Set the address, subnet, and gateway together in one command.
    PS> New-NetIPAddress -InterfaceIndex 12 -IPAddress 192.168.1.12 -PrefixLength 24 -DefaultGateway 192.168.1.1
  3. Set DNS servers
    A separate cmdlet from the IP assignment itself — easy step to forget since name resolution will silently fail without it.
    PS> Set-DnsClientServerAddress -InterfaceIndex 12 -ServerAddresses 8.8.8.8
  4. Confirm it actually applied
    Re-check the adapter after applying — don't assume the config took effect just because no error was shown.
    PS> Get-NetAdapter | Where-Object InterfaceIndex -eq 12
    Unlike a raw ip addr add on Linux, these PowerShell cmdlets persist automatically — no separate step needed to survive a reboot.
  5. Test connectivity end-to-end
    Reach the gateway first, then something beyond it, then confirm DNS-based resolution specifically works too — not just raw IP reachability.
    # Can we reach the gateway?
PS> Test-Connection -TargetName 192.168.1.1 -Count 3

# Can we reach something beyond the local subnet?
PS> Test-Connection -TargetName 8.8.8.8 -Count 3

# Does name resolution actually work, not just raw IP reachability?
PS> Resolve-DnsName -Name example.com
  6. Document the IP scheme
    Record what's assigned where — critical for the team when multiple boxes are being configured together.
▶ E Active Directory & Domain Recon domain environments
Orienting inside a domain, read-only throughout. Only meaningful on a domain-joined box with the RSAT ActiveDirectory module available — confirm that in Track A first if it hasn't been checked yet.
  1. Confirm domain context and which DC authenticated you
    A quick recap beyond Track A's basic domain-joined check — worth knowing exactly which domain controller is currently in play.
    PS> Get-ComputerInfo -Property CsDomain, CsPartOfDomain
PS> $env:LOGONSERVER
  2. Audit domain user accounts
    The domain-wide version of the local account audit from Track B — see Get-ADUser for the full reference.
    PS> Get-ADUser -Filter * -Properties LastLogonDate | Select-Object Name, Enabled, LastLogonDate
    What to look for: an enabled account that hasn't logged on in a long time, or one with a suspiciously recent creation date.
  3. Audit domain-joined computers
    A full inventory of what's actually joined to the domain — see Get-ADComputer for the full reference.
    PS> Get-ADComputer -Filter * | Select-Object Name, DistinguishedName
    What to look for: a computer object that doesn't correspond to a real, known machine.
  4. Audit privileged group membership
    The single highest-value check in this track — one unexpected member of a privileged group has domain-wide impact. See Get-ADGroup / Get-ADGroupMember for the full reference.
    PS> Get-ADGroupMember -Identity "Domain Admins"
PS> Get-ADGroupMember -Identity "Enterprise Admins"
    What to look for: any account in either group that isn't a known, intended administrator.
  5. Confirm PS Remoting reachability to other domain members
    Worth checking before assuming remote management will work when it's actually needed — see Test-WSMan for the full reference.
    PS> Test-WSMan -ComputerName <other domain member>
  6. Confirm Group Policy is current before drawing conclusions
    Force a refresh first, so anything reviewed afterward reflects the domain's actual current policy rather than a stale local cache — see gpupdate for the full reference.
    C:\> gpupdate /force
  7. Document findings
    Domain-wide findings — especially privileged group membership — are worth escalating and recording immediately, not just noting for later.
▶ F IIS Web Server Setup changes the system
Standing up and configuring Internet Information Services as a web server role. See IIS for the full tool reference.
  1. Install the IIS role
    Unlike Apache on Linux, there's no separate package index to refresh first — installing the role is the whole step.
    PS> Install-WindowsFeature -Name Web-Server
  2. Confirm it's actually running
    The IIS Windows service is named W3SVC internally, not "IIS" — see Get-Service's Notes on display name vs. service name if that's unfamiliar.
    PS> Get-Service -Name W3SVC
    Results from Get-Service -Name W3SVC
    Status: Running
    MeansIIS started successfully — move on to the next step
    Status: Stopped
    MeansIt didn't start — check Get-WinEvent against the System log for the specific error before assuming the role install itself failed
  3. Find the web root
    IIS's default is C:\inetpub\wwwroot, but it's configured per-site rather than hardcoded — worth confirming rather than assuming, especially on a box someone else set up.
    PS> Get-Website | Select-Object Name, PhysicalPath
  4. Replace the default page — pick whichever fits the content
    Two options depending on how much content there is and where it's coming from.
    # Option 1: short content, written directly
PS> Set-Content -Path C:\inetpub\wwwroot\index.html -Value '<h1>My IIS Website</h1><p>IIS is working.</p>'

# Option 2: importing an existing file, or a whole site's worth of files
PS> Copy-Item -Path .\mypage.html -Destination C:\inetpub\wwwroot\index.html
PS> Copy-Item -Path .\mysite\* -Destination C:\inetpub\wwwroot\ -Recurse
  5. Verify the page locally
    Confirms IIS is actually serving the updated content, without needing a browser.
    PS> Invoke-WebRequest http://localhost
  6. If the page doesn't load but the box is otherwise reachable
    Confirm something is actually listening on port 80 before assuming IIS itself is broken.
    PS> Get-NetTCPConnection -LocalPort 80
▶ G Database Setup (MySQL) changes the system
GUI-preferred: assumes MySQL Server is already installed via the MySQL Installer GUI — that part isn't CLI-native on Windows, unlike most of the rest of this doc. See mysql for the full client reference.
  1. Confirm the service is actually running
    The Windows service name is typically MySQL80 (or similar, versioned) — confirm the exact name if this doesn't return anything.
    PS> Get-Service -Name MySQL80
  2. Log in and set up a database
    The block below is the actual SQL to run once connected: make a database, switch into it, create a table, add a few rows.
    C:\> mysql -u root -p
    CREATE DATABASE <dbname>;
USE <dbname>;
CREATE TABLE <tablename> (
    id INT PRIMARY KEY AUTO_INCREMENT,
    <column1> VARCHAR(50),
    <column2> VARCHAR(50)
);
INSERT INTO <tablename> (<column1>, <column2>)
VALUES ('<value1>', '<value2>'), ('<value3>', '<value4>');
  3. Verify the data and structure
    Still inside the same session. Confirm the rows are actually there, and that the table/columns look right.
    SELECT * FROM <tablename>;
SHOW TABLES;
DESCRIBE <tablename>;
  4. Create a scoped account for anything that will connect to this database
    Not the root account — see CREATE USER / GRANT for the full reference and the reasoning behind scoping privileges tightly.
    CREATE USER 'webapp'@'localhost' IDENTIFIED BY 'REPLACE_ME';
GRANT SELECT, INSERT, UPDATE ON <dbname>.* TO 'webapp'@'localhost';

    Returns to the regular shell.
    EXIT;
  6. Take a backup once the setup is confirmed working
    Same discipline as any other backup in this doc — take it once things are in a known-good state, not only after something's already gone wrong. See mysqldump.
    C:\> mysqldump -u root -p <dbname> > <dbname>_backup.sql
▶ 04 Reference / Glossary concepts & context
PowerShell Object Pipeline
Everything that moves through a PowerShell pipeline is a real object — not plain text the way it is in cmd.exe or a Unix shell. When one cmdlet's output feeds into another via |, what actually gets passed along are structured objects with real properties, not lines of text that need to be parsed apart. This is why Get-Process | Sort-Object CPU works directly with no text-parsing involved, and it's the whole reason Get-Member exists — it shows exactly which properties an object actually carries before you try to filter or sort on one.
Execution Policy
A safeguard controlling whether PowerShell scripts (.ps1 files) are allowed to run, and under what conditions. It's not a security boundary the way a firewall is — closer to a guardrail against accidentally running a malicious script than an actual barrier against a determined attacker. Common levels: Restricted (the client-edition default — no scripts run at all), RemoteSigned (local scripts run freely, anything downloaded needs a valid digital signature), and Unrestricted (everything runs, signed or not). Check the current setting with Get-ExecutionPolicy, change it with Set-ExecutionPolicy. Worth remembering it's trivially bypassed by anyone with local access (powershell.exe -ExecutionPolicy Bypass) — treat it as a tripwire against accidents, never as real access control.
Verb-Noun Cmdlet Syntax
Every native PowerShell cmdlet follows a strict Verb-Noun naming pattern — Get-Process, Stop-Service, New-Item. The verb describes the action (Get, Set, New, Remove, Start, Stop, and a defined, fairly short list of others), the noun describes what it acts on — both drawn from a standard list Microsoft maintains, not invented freely per module. This predictability is what makes Get-Command genuinely useful: knowing the pattern, you can guess the shape of a cmdlet you've never used, and search confidently by verb or noun alone.
WinRM vs. PS Remoting
WinRM (Windows Remote Management) is the underlying service that actually carries remote management traffic — the transport layer. PS Remoting is PowerShell's specific use of that WinRM transport to run PowerShell commands remotely; it's a capability built on top of WinRM, not a separate service of its own. WinRM itself is often already running by default once a machine joins a domain, but PS Remoting still has to be explicitly turned on with Enable-PSRemoting before Invoke-Command or Enter-PSSession will work. Test-WSMan checks the WinRM layer specifically, which is why it's the right first troubleshooting step when remoting fails — it confirms the transport itself is reachable before anything about PS Remoting's own configuration gets blamed.
The Registry
A hierarchical database Windows stores almost all of its configuration in — application settings, hardware config, OS behavior, and security policy all live here. Organized into a small set of root keys: HKEY_LOCAL_MACHINE (HKLM) holds machine-wide settings that apply regardless of who's logged in, while HKEY_CURRENT_USER (HKCU) holds settings scoped to the logged-in user only. Each root key contains nested keys and, at the bottom, actual values. PowerShell treats the registry as just another provider it can navigate the same way it navigates the filesystem — Get-ChildItem, Get-ItemProperty, and Set-ItemProperty all work against registry paths exactly like they work against files and folders, just with HKLM:\ or HKCU:\ in place of C:\.
GPO & GPMC
A Group Policy Object (GPO) is a bundle of settings — anything from password requirements to which software gets installed — applied to every user or computer inside whatever OU, domain, or site it's linked to. GPMC (Group Policy Management Console) is the tool used to actually create, edit, and link GPOs; authoring one is outside the scope of this doc, which sticks to gpupdate for confirming policy has actually been pulled and applied, rather than building policy from scratch. Every domain gets two GPOs by default: the Default Domain Policy (baseline settings for the whole domain) and the Default Domain Controller Policy (settings specific to DCs). Both are meant to stay mostly untouched — real custom policy is layered on through additional GPOs rather than edited directly into the defaults.
What Is Active Directory?
Active Directory (AD) is Windows' directory service — a centralized database of every user, computer, and group in an organization, along with the permissions and policies that apply to them. Rather than managing accounts and settings on each machine individually the way local accounts work, AD lets an administrator manage all of it from one place, and every domain-joined machine trusts that central source as authoritative. This is why auditing domain accounts with Get-ADUser matters just as much as auditing local accounts with Get-LocalUser — a compromise of AD itself potentially compromises every machine that trusts it, not just one box.
Domain Controllers
A Domain Controller (DC) is a server that actually hosts Active Directory and answers authentication requests — every login, permission check, and policy lookup on a domain-joined machine ultimately traces back to a DC. A domain typically runs more than one DC for redundancy, each keeping a synchronized copy of the same directory. Because a DC holds the keys to the entire domain, it's the single highest-value target in a domain environment — compromising a DC generally means compromising every account and machine that trusts it. On a domain-joined machine, $env:LOGONSERVER shows which DC actually authenticated the current session.
Forest / Domain / OU
The hierarchy Active Directory is organized into, from largest to smallest. A Domain is the core administrative boundary — a namespace with its own set of users, computers, and policies. Multiple domains can be grouped into a Forest, which shares a certain level of trust between the domains inside it. Within a single domain, Organizational Units (OUs) subdivide it further, typically by department or function, mostly so different Group Policy Objects can be targeted at different OUs rather than applied domain-wide. Smaller environments often run a single domain in a single forest with just a handful of OUs; larger ones nest all three layers to control exactly where policy and trust extend.
LDAP
Lightweight Directory Access Protocol (LDAP) is the protocol Active Directory actually uses under the hood to look up and modify directory objects. Cmdlets like Get-ADUser and Get-ADComputer are a PowerShell-friendly layer built on top of LDAP queries; tools outside the PowerShell ecosystem — cross-platform directory browsers, various enumeration tools — often talk LDAP directly instead. Worth recognizing the term even without ever needing to write a raw LDAP query by hand.
DNS's Role in Active Directory
Active Directory depends on DNS working correctly — domain-joined machines locate a Domain Controller by querying DNS for specific AD-related records, not through any hardcoded address. This is why a DNS Server role is typically installed and running right alongside AD DS on most domain controllers. If DNS resolution breaks on a domain-joined machine, authentication and Group Policy application often break along with it — even though the actual failure is DNS, not AD itself. See Resolve-DnsName for the command-level check.
Kerberos vs. NTLM / NetNTLM
Two different authentication protocols Windows uses to prove identity — not interchangeable, and not equally trustworthy. Kerberos is the default and preferred protocol on a domain: a domain-joined machine authenticates using tickets issued by a Domain Controller, and the actual password never crosses the network. NTLM (and its network variant, NetNTLM) is the older challenge-response protocol, still used as a fallback whenever Kerberos isn't available — authenticating to a machine by IP address instead of hostname, or authenticating outside a domain entirely, both fall back to NTLM. NTLM is significantly weaker and a well-known target for relay and cracking attacks; seeing NTLM used where Kerberos should have been possible is worth investigating, not dismissing as routine.
SID (Security Identifier)
A unique identifier Windows assigns to every user, group, and computer account — the real value Windows actually checks for identity and permissions, with the human-readable username or group name being just a friendly label layered on top. Well-known SIDs stay the same across every Windows installation regardless of language or local naming — S-1-5-32-544 is always the local Administrators group, for instance. Deleting and recreating an account with the same name does not preserve its SID or its permissions — the new account is a completely different identity as far as Windows is concerned, even though the username looks identical.
DACL / SACL
Two different parts of an object's Access Control List (see Get-Acl / Set-Acl). The DACL (Discretionary ACL) is what actually determines who's allowed to do what — every allow and deny entry for a file, folder, or registry key lives here. The SACL (System ACL) is separate and controls auditing — which access attempts get logged, not which are permitted. A file can have a perfectly normal DACL and still generate a full audit trail on every access, or the reverse — the two lists are configured independently of each other.
User Account Control (UAC)
The prompt asking to confirm an action that requires administrator privileges, even while already logged in as an administrator. The point isn't adding a password step to every admin action — an administrator's account token is deliberately split into a standard-privilege half used for everyday work and a full-privilege half only invoked when something specifically requires elevation, which is exactly what the prompt triggers. This limits the blast radius of anything running under that account day-to-day: a compromised process without an explicit elevation prompt doesn't automatically inherit full admin rights just because the logged-in user has them available. Controlled through the registry — see the EnableLUA example under Set-ItemProperty.
Service Display Name vs. Service Name
Every Windows service has two names: a human-readable Display Name ("World Wide Web Publishing Service") and a short, internal Service Name that most command-line tools actually expect (W3SVC). Get-Service's -Name parameter wants the short service name, not the display name — use -DisplayName instead if that's what's on hand. This trips people up constantly, especially with services whose short name has no obvious relationship to the display name at all — W3SVC for IIS being a good example. Worth confirming the actual mapping through Get-Service rather than guessing at it.
Roles & Features
Windows Server's two categories of optional, install-on-demand functionality. A Role is a major function the server is built to provide — IIS as a web server, AD DS to act as a domain controller, DNS Server. A Feature is smaller and more supporting in nature, sometimes standalone and sometimes required by a specific role. Neither is present out of the box; both get installed with Install-WindowsFeature and reviewed with Get-WindowsFeature — both of which only exist on Server editions in the first place, since a Client edition doesn't have the Roles & Features concept at all. An unexpected installed role is one of the clearest signs a box has been altered from its intended purpose.
Host Services vs. Business Services
Two different ways to think about the word "service," worth distinguishing since they don't always overlap 1:1. A Host Service is a background process running on a machine — anything Get-Service can show, whether or not anyone outside the box actually cares whether it's running. A Business Service is the actual functionality being delivered — a public-facing website, an internal file share — regardless of how many host services combine underneath to make it work. A box can run a dozen host services while only one or two actually back a business service that matters. This is exactly what deciding whether "the juice is worth the squeeze" depends on — see Track C's SSH/FTP example — since hardening or troubleshooting a host service nobody relies on is wasted effort next to the business service that's actually depended on.
Threat Modeling & Prioritization
A structured way to reason about whether and how to secure a service, rather than reacting to each one ad hoc. Three questions, worked through in order: Functionality — what role does this service play in the business, and how does it actually work from a technical standpoint? Attacks — what would actually impact that role (denial of service, defacement, command execution, information exposure), and what does an attacker genuinely need to pull it off (network access, authentication, a specific misconfiguration)? Mitigations — is there a configuration change or patch that removes what the attack requires, and can the impact be isolated even where it can't be fully prevented? Paired with a cost/benefit lens worth applying throughout: the goal is the most impact for the least effort under real time pressure, not a theoretically perfect defense of everything at once. See Incident Response Ordering for the same discipline applied after something's already gone wrong, rather than before.
Incident Response Ordering
A general priority order worth internalizing rather than following as a rigid checklist — real incidents rarely go cleanly in sequence, but the underlying priority stays consistent. Contain first: cutting off active unauthorized access matters more than fully understanding it in the moment — see Track C/D for isolating a box at the firewall or network level, or Stop-Process/taskkill to kill an active malicious process outright. Preserve evidence next, before cleaning anything up — hash a suspicious file with Get-FileHash and check its signature with Get-AuthenticodeSignature before deleting or moving it — evidence gone is gone for good. Remove persistence third — check Scheduled Tasks, Services, and registry Run keys (Get-ScheduledTask, Get-Service, Get-ItemProperty) for whatever's letting access survive a reboot, and clear it out. Patch the actual vector fourth — the specific misconfiguration, missing patch, or exposed credential that allowed entry in the first place; removing an attacker's foothold without fixing how they got in just invites a repeat. Document throughout, not only at the end — Export-Csv turns any of the above into something that can actually be handed off or reported on. The instinct to jump straight to cleanup is natural, and usually wrong — evidence and containment come first, or there's nothing left to learn from once it's over.

▶Where to Look, and How— Microsoft Learn, SS64, Stack Overflow/Server Fault, LOLBAS, ADMX.help

Best for: the exact, authoritative syntax and every parameter a cmdlet supports — the same source Get-Help -Online opens directly to.

How to actually search it: search "<cmdlet name> Microsoft Learn" rather than browsing — it's consistently the top result and lands directly on the reference page, including every parameter set the cmdlet supports.

SS64 ↗

Best for: a fast, dense syntax reference for both PowerShell and cmd.exe commands — far less prose than Microsoft Learn, easier to scan when the goal is just remembering a flag.

How to actually search it: ss64.com/ps/<cmdlet>.html for PowerShell cmdlets, ss64.com/nt/<command>.html for cmd.exe-lineage commands like reg or icacls.

Server Fault ↗ / Stack Overflow ↗

Best for: "why is this specific thing happening" — a real error message or unexpected behavior, not general learning.

How to actually search it: search the exact error text in quotes rather than describing the problem in your own words. Don't stop at the top-voted answer — a lower one is sometimes the more current fix, especially on an older question.

LOLBAS Project ↗

Best for: understanding exactly how a legitimate, built-in Windows binary gets abused for malicious purposes — the same "living off the land" idea behind Invoke-Expression's Caution note, catalogued across dozens of binaries.

How to actually search it: search by the binary or cmdlet name directly — each entry lists the specific abuse techniques documented for it, with real command examples.

ADMX.help ↗

Best for: looking up what a specific Group Policy setting actually controls before enabling it — a searchable version of every built-in GPO setting Microsoft ships.

How to actually search it: search the setting's exact display name as it appears in GPMC — results include the underlying registry key it maps to, which is often the faster path if the goal is setting it via Set-ItemProperty instead of through Group Policy itself.
